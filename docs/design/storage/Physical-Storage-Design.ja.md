# 物理ストレージ設計仕様書

> 言語: [English](Physical-Storage-Design.md) | **日本語**

本プロジェクトのストレージエンジンは、PostgreSQL の内部構造をモデルにした **Slotted Page（スロットページ）** レイアウトを採用しています。固定サイズのページ内で可変長レコードを効率的に管理し、ディスク I/O を最小化します。

---

## 1. レイアウト定数

`internal/storage/slotted_page.go` の定数と 1 対 1 で対応します。

| 定数              | 値    | 意味                                        |
| :---------------- | :---- | :------------------------------------------ |
| `PageSize`        | 8192  | ページサイズ（バイト、8 KB、PostgreSQL 既定値） |
| `HeaderSize`      | 24    | ページヘッダーのサイズ（バイト）            |
| `SlotEntrySize`   | 4     | スロットエントリ 1 個のサイズ（バイト）     |
| `TupleHeaderSize` | 12    | タプルヘッダーのサイズ（バイト）            |

8 KB は現代の SSD（特に Apple Silicon の NVMe SSD、本プロジェクトの対象環境）のブロックサイズと親和性が高い設定です。

---

## 2. ページレイアウト

標準のページサイズは **8,192 バイト（8 KB）** です。スロットディレクトリはヘッダー直後から下方向へ、タプルデータはページ末尾から上方向へ成長し、両者の間（`pd_upper` … `pd_lower`）が空き領域になります。

> **命名に関する注意。** `pd_lower` / `pd_upper` は、ページを上から下へ描いた図に基づく命名であり、アドレス値に基づくものでは **ありません**（PostgreSQL とは異なります）。`pd_upper` はスロットディレクトリを区切る *低い* アドレス、`pd_lower` はタプルデータが始まる *高い* アドレスです。したがって常に `pd_upper < pd_lower` となります。

## 3. ページヘッダー（24 バイト）

複数バイトのフィールドはすべて **ビッグエンディアン** です。

| オフセット | 長さ | 名称           | 説明                                                             |
| :--------- | :--- | :------------- | :--------------------------------------------------------------- |
| 0          | 8    | `pd_lsn`       | Log Sequence Number。ページを最後に変更した WAL レコードの識別子。 |
| 8          | 2    | `pd_checksum`  | 書き込み時の整合性チェック用チェックサム。                       |
| 10         | 2    | `pd_flags`     | ページのステータス（空きあり、インデックス用など）。             |
| 12         | 2    | `pd_lower`     | **空き領域の下端** — タプルデータ区の開始位置（次のタプルが置かれる位置）。タプル追加に伴い減少。 |
| 14         | 2    | `pd_upper`     | **空き領域の上端** — スロットディレクトリの末尾（次のスロット追加位置）。スロット追加に伴い増加。 |
| 16         | 2    | `pd_special`   | Special 領域 — インデックス（B-Tree の前後ページポインタ等）で使用。 |
| 18         | 2    | `pd_pagesize`  | ページサイズとレイアウトバージョンの識別。                       |
| 20         | 4    | `pd_prune_xid` | 不要タプルをプルーニング（VACUUM）可能な最古トランザクション ID。 |

---

## 4. スロットディレクトリとスロットエントリ（各 4 バイト）

スロットディレクトリは、固定 4 バイトの **スロットエントリ** の配列で、`[HeaderSize, pd_upper)` を占めます。各エントリは間接参照として機能し、ページ内でタプルが物理的に移動しても、スロット番号（ID）は固定されます。

### スロットエントリのビットレイアウト（32 ビット、ビッグエンディアン）

```
bit 31                    17 16                      2 1        0
+---------------------------+--------------------------+---------+
|        Offset (15b)       |        Length (15b)      |Flags(2b)|
+---------------------------+--------------------------+---------+
```

| フィールド | ビット | 範囲       | 意味                                             |
| :--------- | :----- | :--------- | :----------------------------------------------- |
| `Offset`   | 15     | 0 – 32767  | ページ内でのタプルの開始オフセット。             |
| `Length`   | 15     | 0 – 32767  | スロットが指すタプルのバイト長。                 |
| `Flags`    | 2      | 下記参照   | スロット（行ポインタ）の物理状態。               |

### スロットフラグ（行ポインタの状態）

| 値   | 名称       | 意味                                                        |
| :--- | :--------- | :---------------------------------------------------------- |
| `00` | `UNUSED`   | 空きスロット。再利用可能。                                  |
| `01` | `NORMAL`   | 有効なタプルを指す。                                        |
| `10` | `DELETED`  | タプルは無効。VACUUM 後に再利用可能。                       |
| `11` | `REDIRECT` | 別スロットへリダイレクト（更新チェーン / HOT 用）。         |

> これらのフラグは MVCC の可視性とは独立した、行ポインタの **物理状態** を表します。論理的な可視性はタプルの `t_xmin` / `t_xmax`（第 5 章）で判定します。

---

## 5. タプル

タプルは **タプルヘッダー → null ビットマップ（任意）→ 列データ** の順に配置されます。

```
0            12            t_hoff                          Length
+------------+-------------+--------------------------------+
| TupleHeader| null_bitmap |          column data           |
|  12 bytes  | ceil(n/8)   |                                |
+------------+-------------+--------------------------------+
```

- `null_bitmap` は `HASNULL` ヒントビットが立っている場合のみ存在し、列ごとに 1 ビットを持ちます。
- `t_hoff` はタプル先頭から列データまでのオフセット、すなわちヘッダーと null ビットマップを飛ばした位置を指します。タプル総長は `SlotEntry.Length` が保持しているため、冗長な総サイズフィールドをこれで置き換えます。

### 5.1 タプルヘッダー（12 バイト、ビッグエンディアン）

| オフセット | 長さ | フィールド                     | 説明                                                       |
| :--------- | :--- | :----------------------------- | :--------------------------------------------------------- |
| 0          | 4    | `t_xmin`                       | タプルを **挿入** したトランザクションの ID。              |
| 4          | 4    | `t_xmax`                       | タプルを **削除** したトランザクションの ID。`0` は有効（未削除）。 |
| 8          | 2    | `flags`(6b) + `col_count`(10b) | MVCC ヒントビット（6 ビット）+ 列数（10 ビット、0–1023）。 |
| 10         | 1    | `t_hoff`                       | タプル先頭から列データまでのオフセット。                   |
| 11         | 1    | —                              | 予約（パディング / 将来用）。                              |

### 5.2 MVCC ヒントビット（6 ビットの `flags` フィールド）

ヒントビットは `t_xmin` / `t_xmax` のコミット／アボート状態をキャッシュし、可視性判定でトランザクション状態ログ（CLOG、トランザクション層で導入）への参照を回避します。

| ビット | 名称             | 意味                                       |
| :----- | :--------------- | :----------------------------------------- |
| 0      | `HASNULL`        | ヘッダーの後に null ビットマップが続く。   |
| 1      | `XMIN_COMMITTED` | 挿入トランザクションがコミット済みと確定。 |
| 2      | `XMIN_ABORTED`   | 挿入トランザクションがアボート済みと確定。 |
| 3      | `XMAX_COMMITTED` | 削除トランザクションがコミット済みと確定。 |
| 4      | `XMAX_ABORTED`   | 削除トランザクションがアボート済みと確定。 |
| 5      | —                | 予約。                                     |

### 5.3 可視性ルール（簡略版）

タプルがスナップショット **S** から可視であるのは、次を満たすときです:

1. `t_xmin` がコミット済みで **S** から可視、**かつ**
2. `t_xmax` が無効（`0`）、**または** 削除トランザクションがアボート済み、**または** まだコミット／**S** から可視でない。

完全な評価はトランザクション状態ログとスナップショットのロジックに依存し、それらはトランザクション層に属します。ストレージ層は、このルールが要求するフィールド（`t_xmin`、`t_xmax`、ヒントビット）を確保するのみです。

## 6. コアロジック：双方向成長

スロットページの最大の特徴は、2 つの領域が **互いに向かって** 成長することです:

1. **スロットディレクトリ** はヘッダー直後から下方向へ成長します。各 4 バイトのエントリはタプルの位置（`Offset`）と長さ（`Length`）を記録します。スロット番号が固定されているため、ページ内でタプルを再配置しても参照は無効になりません。
2. **タプルデータ** はページ末尾から上方向へ成長します。
3. **空き領域** は `pd_upper`（スロットディレクトリの末尾）と `pd_lower`（タプルデータの先頭）の間の隙間です。`pd_upper + SlotEntrySize > pd_lower` となった時点で、そのページは **Full** と判定されます。
