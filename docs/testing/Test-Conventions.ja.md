# テスト規約

> 言語: [English](Test-Conventions.md) | **日本語**

全モジュール共通のテストルール。モジュール固有のテスト計画は対応するサブディレクトリ（例: [`storage/`](storage/)）に置き、そのモジュール固有の内容のみを記述します。

---

## 1. フレームワーク

標準ライブラリのみ。`testing` パッケージを `go test` で駆動します。**サードパーティのアサーション／モックライブラリは使用しません** — 依存を最小限に保ち、仕組みを明示的にするためです。

---

## 2. ファイルの場所と命名

- テストファイルは **コードと同じディレクトリ** に置き、`<ソース>_test.go` と命名します（例: `slot_entry.go` → `slot_entry_test.go`）。
- `_test.go` で終わるファイルは `go test` のときだけコンパイルされ、通常の `go build` の成果物には含まれません。
- テスト関数は `func TestXxx(t *testing.T)`。名前付きサブテストには `t.Run(name, ...)` を使います。

---

## 3. パッケージの選択：ホワイトボックス vs ブラックボックス

| パッケージ宣言       | 種類           | アクセス可能         | 用途                                       |
| :------------------- | :------------- | :------------------- | :----------------------------------------- |
| `package <pkg>`      | ホワイトボックス | 非公開メンバー       | バイトレイアウト／内部構造の検証           |
| `package <pkg>_test` | ブラックボックス | 公開 API のみ        | 公開契約／往復（round-trip）の検証         |

両方を使います。バイトレイアウトのテストは非公開のバッキング配列が必要なのでホワイトボックス、公開契約を検証するテストは内部に結合しないようブラックボックスにします。

## 4. パターン

### 4.1 テーブル駆動テスト

ケースを構造体スライスに列挙し、`t.Run` でループします。ビットフィールドと境界値のカバレッジに最適 — 1 つのテーブルで多数のケースを網羅します。

```go
tests := []struct {
    name string
    in   uint16
    want uint16
}{
    {"zero", 0, 0},
    {"max", 32767, 32767},
}
for _, tt := range tests {
    t.Run(tt.name, func(t *testing.T) { /* ... */ })
}
```

### 4.2 ゴールデンバイトレイアウト検証

生バイトにマッピングされる型では、期待する生バイトをハードコードして比較します。オフセットの誤りやバイト順の誤りを捕捉できる唯一の方法です — 同じ誤ったオフセットを共有する getter/setter ペアは、互いに一致してしまい誤りを隠します。実装と同じシフト計算で期待値を再計算してはいけません。コードから写した式は、そのコードのバグと一緒に動いてしまいます。手計算でバイト列を導き、導出過程をコメントに残します。

プローブ値は任意ではなく、意図を持って選びます。各フィールドの値は:

- **非ゼロ** — 「正しく書けた」と「そもそも書いていない」を区別できるように;
- 他のすべてのフィールドと **相異なる** — フィールドの取り違えを検出できるように;
- バイト反転に対して **非対称** — バイト順の誤りが見えるように（`0x1111` では隠れてしまう）;
- ビットパックされたフィールドでは **0 でも最大値でもない**、できれば **交互のビットパターン** — 全 0 / 全 1 のフィールドは 1 ビットずれたマスクを隠します。2 ビットのフィールドなら、2 つのビットが異なる `0b10` が `0b00` や `0b11` より優れています。

`0x01020304` のような「バイトの階段」は複数バイトのフィールドに good なプローブです。並び替えや 1 バイトのずれが一目で分かります。これらの値はレイアウトのプローブであり、意味的に妥当なレコードではありません — 組み合わせに意味を持たせようとしないでください。

### 4.3 バイトマッピング型が必ずカバーすべき項目

- **往復（Round-trip）**: `set` の後 `get` が同じ値を返す。
- **フィールド独立性**: あるフィールドの書き込みが隣接フィールドを破壊しない（ビットパック型では重要）。**ゼロ背景と全 max 背景の両方向** で実施すること — はみ出し書き込みは背景と値が異なるときにしか見えないため、ゼロ背景だけでは 0 ビットのはみ出しを、max 背景だけでは 1 ビットのはみ出しを見逃す。max 背景は加えて、setter が OR するだけでなく実際にビットをクリアしていることも証明する。
- **境界値**: `0`、フィールドの最大値、最大値 +1。
- **エラーパス**: サブ幅の setter は範囲外入力を拒否する。

## 5. コマンド

```bash
go test ./...                          # 全テスト
go test -v ./internal/storage/...       # 詳細出力（ケースごとに 1 行）
go test -run TestSlotEntry ./internal/storage/... # 名前でフィルタ
go test -cover ./internal/storage/...   # カバレッジ率
go test -race ./...                    # データ競合検出（並行コード用）
```

---

## 6. ブランチとコミット

- テストは一等コードです。カバー対象のコードと **常に一緒にコミット・マージ** し、未コミットのまま放置しません。
- テストはコード対象と **同じ feature ブランチ** に書きます。テスト専用のブランチは作りません。
- Conventional Commits の `test` タイプでコミットします。例: `test(storage): cover slot entry bit packing`。
