# ヒープアクセスメソッド設計

> 言語: [English](Heap-Design.md) | **日本語**

ヒープアクセスメソッド（`internal/access/heap`）は、テーブルの行を **ヒープファイル**（ページに散らばった*順序なし*のタプルの山）として、バッファプールの上に格納する。「ヒープ」は順序なしの構成を指す名前であり（PostgreSQL のヒープアクセスメソッドと同様）、メモリでもヒープデータ構造でもない。

```
        エグゼキュータ / SQL（将来）
              │  Insert / Get / Scan
              ▼
        Heap  （本モジュール）  ── ページをタプルに変える
              │  FetchPage / NewPage / UnpinPage / NumPages
              ▼
        BufferPool → DiskManager
```

---

## 1. タプルの同一性 — TID

タプルの物理アドレスは **TID**（tuple id）:

```
TID = { Page: disk.PageID, Slot: uint16 }
```

`Page` はファイル内のページ番号、`Slot` はそのページ内のスロットディレクトリの添字。スロットは間接参照であり（将来のページ内コンパクションでタプルが動いてもスロット番号は不変）、TID は **安定したハンドル** となる: 追い出し/再ロードやファイルのクローズ/再オープンをまたいでも有効で、将来のインデックスは TID で行を指せる。

---

## 2. 不透明性

タプルのバイトは heap にとって **不透明**。タプルの組み立て（`TupleHeader`・null ビットマップ・列データ）と解釈（型、MVCC 可視性）は上の層 — レコード/エンコード層、後のトランザクション層 — の担当。heap はバイトをページに置き、返すだけ。

---

## 3. 操作（v1）

| 操作 | 振る舞い |
| :-- | :-- |
| `Insert(data) → TID` | タプルをページに追記し、TID を返す。 |
| `Get(TID) → []byte` | タプルのバイトの **コピー** を返す。 |
| `Scan(fn) → error` | 物理順に全タプルを訪れ、各々に `fn(TID, data)` を呼ぶ。 |

**Insert — ページ選択。** まず **最後の** ページを試し、収まらなければ（`page.ErrNoSpace`）ファイルを 1 ページ拡張（`NewPage`）してそこへ挿入する。この v1 戦略は前方のページの空きを探さない — まだフリースペースマップがないため、前方ページで空いた領域は再利用されない（負債参照）。

**Get — コピーして返す。** ページを unpin する前にタプルのバイトをコピーする。unpin 後はそのフレームが追い出され別ページに再利用され得るため。返したスライスは呼び出し側のもの。

**Scan — コールバック形式。** `Scan(fn func(TID, []byte) error) error` はループを内部で駆動し（ページごと、スロットごと）、タプルごとに `fn` を呼ぶ。コールバックは `nil` で継続、エラーで早期停止し、そのエラーと任意の I/O エラーが `Scan` から返る。range 形式のイテレータ（`iter.Seq2`）でなくコールバック形式なのは、スキャンが失敗し得るディスク I/O を伴い、`iter.Seq2` にはそのエラーを返す場所がないため。`fn` に渡す `data` は呼び出し中のみ有効な **ビュー** — 保持するならコピーする。

---

## 4. 依存 — `pager` インタフェース

heap は具体型 `*buffer.BufferPool` ではなく、小さな消費者側インタフェースに依存する:

```go
type pager interface {
    FetchPage(pid disk.PageID) (*page.Page, error)
    NewPage() (*page.Page, disk.PageID, error)
    UnpinPage(pid disk.PageID, dirty bool) error
    NumPages() disk.PageID
}
```

実装ではなく能力（ページを供給するもの）に因んだ名前。結合を小さく保ち、テストがオンデマンドで失敗するフェイクプールを差し込め、将来別のページ供給元の余地も残す。`*buffer.BufferPool` がこれを満たす。

プールが供給するのは **生フレーム**（`*page.Page`）である。8 KB のバイト列を所有するが、レイアウトは押し付けない。heap は `page.AsSlottedPage(raw)`（ゼロコピーのビュー）で自分の解釈を被せる。こうしてバッファプールは異なる種類のページのファイル（ここでは heap ファイル、別の場所では B+Tree インデックスファイル）を 1 つのキャッシュで同一のまま扱える。`NewPage` はゼロ初期化された未フォーマットのフレームを返し、heap が `Init` で整形する。その整形はメモリ上にしか存在しないため dirty にして unpin し、ディスクへ届ける — タプルが大きすぎて入らない場合でも同様で、後の `Scan` が誤読する未フォーマットのページをファイルに残さない。

---

## 5. 先送り（と将来の帰属先）

- **Update / Delete** — heap に属するが MVCC/トランザクション層が必要。更新は生きたタプルを上書きせず、**新バージョン**を追記して旧版を `t_xmax` を立てて死とマークする。削除は `t_xmax` を立てるだけ。よってタプルデータは実質追記のみで、`TupleHeader` に既にある `t_xmin`/`t_xmax` がその仕組み。
- **VACUUM** — どのトランザクションからも見えなくなった死んだタプル版の領域を物理的に回収する独立の保守操作（ページ内コンパクション + 死スロット再利用）。
- **フリースペースマップ** — 「最後のページ、なければ新規」より賢いページ選択。
- **並行性** — `Insert` はプールロックの外でページ内容を変更するため、v1 の heap は並行安全でない（バッファプールのページ単位ラッチ待ち）。
- **大きなタプル** — ページより大きいタプルは拒否。オーバーフロー/TOAST 格納は将来の課題。
