# システムカタログ設計

> 言語: [English](Catalog-Design.md) | **日本語**

システムカタログ（`internal/catalog`）は**データに関するデータ**の格納庫である。どんなテーブルが存在するか、その列スキーマ、各テーブルを支えるファイル、そしてそれらの上のインデックス。Table 層と SQL 層が土台にする**名前解決の権威**であり、`users` のような名前をスキーマ・heap ファイル・インデックス群へと変える。

```
        SQL / executor（将来）
              │  "users" -> スキーマ, heap ファイル, インデックス
              ▼
        Catalog（本モジュール）   ── メタデータのみ; ファイル名を記録
              │  1 つの JSON 文書を読み書き
              ▼
        catalog.json（データベースディレクトリ内）
```

これまでスキーマは呼び出し側がメモリ上で `record` 層に手渡していた。カタログはそれを永続化し、再オープンしたデータベース — そして SQL の名前解決 — が何が存在するかを知れるようにする。

---

## 1. 範囲

カタログは**メタデータのみを記録**する。ファイルを開き、バッファプールに登録し、テーブルの heap とインデックスを結線するのは **Table 層**（次モジュール）の仕事; カタログはファイルの*名前*だけを保持する。

| 操作 | 挙動 |
| :-- | :-- |
| `Open(dir) → *Catalog` | `dir` 下のカタログを読み込む（無ければ `dir` と空カタログを作成）。 |
| `CreateTable(name, schema) → TableMeta` | テーブルを記録し heap ファイルを割り当て、永続化。 |
| `CreateIndex(table, name, column) → IndexMeta` | テーブルの列にインデックスを記録しファイルを割り当て、永続化。 |
| `GetTable(name) → (TableMeta, bool)` | 名前でテーブルを解決。 |
| `ListTables() → []TableMeta` | 全テーブルを名前順で。 |
| `Dir() → string` | ディレクトリ。呼び出し側が meta の `File` をフルパスに解決するため。 |

**延期:** `Drop` / `Alter`（ファイル回収と、列変更にはデータ書き換えが要る）。

---

## 2. メタデータの形

```go
type TableMeta struct {
    Name    string
    Schema  record.Schema   // record 層のスキーマを再利用
    File    string          // このテーブルの heap ファイル名
    Indexes []IndexMeta
}

type IndexMeta struct {
    Name   string
    Column int              // テーブルスキーマの何列目か
    File   string           // インデックスファイル名
}
```

`record.Schema` を再利用することで、「テーブルの列」の定義がエンコード/デコード層とカタログで 1 つに保たれる。

---

## 3. 格納: ストアインタフェースの後ろの JSON 文書

カタログは DB ディレクトリ内の**単一 JSON ファイル**（`catalog.json`）として永続化し、DDL ごとに書き直す。v1 で JSON を選ぶのは、単純で人間可読だから — 開発中に `catalog.json` を開けばデータベースの構造がそのまま見える。

ファイル I/O は小さな `blobStore` インタフェース（`load`/`save`）の後ろに置く。バッファプールが `diskManager` の後ろに置かれるのと全く同じ:

- **本番**は `fileStore` を使い、JSON ファイルを読み、save 時はテンポラリファイルへ書いてからターゲットへ rename する — 書き込み途中のクラッシュが半端なカタログを残さないように。
- **テスト**は `load`/`save` をオンデマンドで失敗させる `fakeStore` を注入し、エラー・ロールバック経路を決定論的に駆動する。

肝心なのは、呼び出し側が依存するのは `Catalog` *インタフェース*だけで、JSON 格納は隠されていること。将来（PostgreSQL の `pg_class`/`pg_attribute` 流の自己記述 heap テーブルなどに）差し替えても、**上位層は変わらない**。その正統だが重い設計は自己記述の鶏卵問題（テーブルを記述するテーブルをどう読むか）を抱えるため延期する; インタフェースが差し替えをローカルな変更にする。

---

## 4. ファイル命名 — 共有カウンタ

`CreateTable` と `CreateIndex` は 1 つの単調カウンタ（`NextID`）からファイルを割り当て、`rel_<id>.db` と名付ける — PostgreSQL の *relfilenode* 流。名前（テーブル/列名）から導くのではなくカウンタにするのは、**リネームに強く**、命名衝突が無いから。カウンタは永続化状態の一部なので、再オープンをまたいで id は増え続ける。

---

## 5. 永続化とロールバック

各変更はメモリ状態に適用してから `persist` を呼ぶ。書き込みが失敗したら、その変更は**メモリ上でロールバック**される — 新しいテーブル/インデックスを取り除き、id カウンタを戻す — のでメモリとディスクが乖離しない。呼び出し側に返すメタデータ（`GetTable`・`ListTables`）は**ディープコピー**なので、返されたスキーマやインデックス一覧を呼び出し側が変更してもカタログを壊せない。

---

## 6. 延期（将来の置き場所つき）

- **Drop / Alter** — drop はリレーションのファイルを回収する必要（ディスクの空き回収と対）; 列の alter はデータ書き換えが要る。両者はその仕組み待ち。
- **カタログを heap テーブルに** — カタログを自己記述テーブル（`pg_class`/`pg_attribute` 流）に格納し、SQL で問い合わせ可能にする（bootstrap スキーマはハードコード）。`blobStore` の継ぎ目がこれを内部差し替えにする。
- **record 層を超える制約・型** — 主キー、一意性、外部キー、より豊かな列型は、SQL 層が必要とした時点でここに入る。
