# B+Tree インデックス設計

> 言語: [English](BTree-Index-Design.md) | **日本語**

B+Tree アクセスメソッド（`internal/access/nbtree`）は**セカンダリインデックス**である。`int64` の key を、その key を持つ行の `heap.TID` に対応づけ、クエリがヒープ全体を走査せずに値から行を見つけられるようにする。ディスク指向の B+Tree で、各ノードが 1 ページ、ノードの扇出が高く、木は浅いまま（現実的なテーブルなら 3〜4 層）である。

```
        executor / SQL（将来）
              │  Insert(key,tid) / Search(key) / Scan(lo,hi)
              ▼
        BTree（本モジュール）   ── ページをソート済み key → TID マップにする
              │  FetchPage / NewPage / UnpinPage / NumPages
              ▼
        BufferPool → DiskManager   （専用のインデックスファイル）
              │
        heap.TID ─────────────────► Heap（TID → 行バイト列に解決）
```

---

## 1. 目的 — なぜインデックスか

ここまでのストレージエンジンは、**既知の** `heap.TID` でしか行を読めない。実際のクエリは値で絞り込み（`WHERE age = 42`）、手元に TID はない。インデックスがなければ唯一の手段は**ヒープ全走査** — 全ページを読み、全行をデコードし、比較する — で `O(N)` になる。

B+Tree インデックスは key 値 → TID の**ソート済み**マップを事前構築する。下降は key 数に対して `O(log N)`、扇出が数百なので、数億行でもその対数は 3〜4 回のページ読みで済む。インデックスは「この key／この範囲の key を持つ TID はどれか」に答え、ヒープが各 TID を実際の行に解決する。

---

## 2. ファイル格納戦略

- **インデックス 1 つにつきファイル 1 つ。** インデックスはヒープテーブルの 1 列上に作られ、1 テーブルは複数のインデックスを持ちうる。どのインデックスがどのテーブル／列に属すかは**システムカタログ**の仕事（延期）。v1 ではインデックスファイルは専用の `DiskManager` と専用の `BufferPool` インスタンスに束ねられる — v1 のプールは 1 ファイルしかキャッシュしないため、ヒープのプールとは別のメモリ予算になる（負債: 複数ファイルプール参照）。
- **インデックスファイルはページの山**で、ヒープファイルと同じだが、ページのレイアウトはスロット付きページではなく **B+Tree ノード**である。バッファプールは生の `*page.Page` フレームを供給しレイアウトを課さない。`nbtree` は `p.Bytes()` に**ノードビュー**を被せる — `heap` が `AsSlottedPage` を被せるのと全く同じで、これがフレーム型をレイアウト非依存にした理由である。

```
インデックスファイル
┌──────────┬──────────┬──────────┬──────────┬─────
│ page 0   │ page 1   │ page 2   │ page 3   │ ...
│ meta     │ node     │ node     │ node     │
└──────────┴──────────┴──────────┴──────────┴─────
   ▲ root_pid ──────────► 現在の root ノード（root 分裂で移動する）
```

- **page 0 は meta ページ**でノードではない。どのページが現在の root かを記録する固定アンカーである。root のページ id は root が分裂するたびに変わるため、root 自身を固定位置にはできない — meta ページがその役を担う。
- **page 1 以降がノード。** 各ノードは**内部**ノード（検索を下へ誘導）か**葉**ノード（実際の key → TID エントリを持つ）のいずれか。データは**葉にのみ**存在し、内部ノードは separator key だけを持つ。

## 3. レイアウト定数

| 定数             | 値    | 意味                                            |
| :--------------- | :---- | :---------------------------------------------- |
| `PageSize`       | 8192  | ページサイズ（バイト、`internal/storage/page` 由来） |
| `NodeHeaderSize` | 8     | ノードヘッダーのサイズ（バイト）                |
| `MetaMagic`      | —     | インデックスファイルを識別するマジックナンバー  |
| `KeySize`         | 8    | `int64` key、ビッグエンディアン                 |
| `ChildSize`       | 4    | 子ポインタ = `disk.PageID`（`uint32`）          |
| `TIDSize`         | 6    | 葉の値 = `heap.TID` = `PageID(4) + Slot(2)`     |
| `MaxInternalKeys` | 681  | 内部ノードの固定 key 容量                       |
| `MaxLeafKeys`     | 584  | 葉ノードの固定 key 容量                         |
| `ChildAreaOff`    | 5456 | 子配列の固定開始オフセット（`8 + MaxInternalKeys·8`） |
| `TIDAreaOff`      | 4680 | TID 配列の固定開始オフセット（`8 + MaxLeafKeys·8`） |

マルチバイトフィールドはすべて**ビッグエンディアン**。

---

## 4. Meta ページ（page 0）

meta ページは 1 ページで、生きている中身は root ポインタだけ。全操作の冒頭で読まれ（プール内で常にホット）、root が変わったときだけ書き換えられる。

| オフセット | 長さ | フィールド | 説明                                               |
| :--------- | :--- | :--------- | :------------------------------------------------- |
| 0          | 4    | `magic`    | ファイルが nbtree インデックスであることを識別。   |
| 4          | 4    | `root_pid` | 現在の root ノードのページ id。                    |
| 8          | …    | —          | 予約（将来: 空きページリスト、高さ、key 型）。     |

---

## 5. ノードページ

### 5.1 ノードヘッダー（8 バイト）

両種のノードで共有。

| オフセット | 長さ | フィールド  | 説明                                                        |
| :--------- | :--- | :---------- | :---------------------------------------------------------- |
| 0          | 1    | `node_type` | `1` = 葉、`0` = 内部。                                      |
| 1          | 1    | —           | 予約（将来: level / flags）。                              |
| 2          | 2    | `key_count` | このノードの key 数 `N`。                                  |
| 4          | 4    | `next_leaf` | 葉のみ: 右隣の葉のページ id（最後の葉と内部ノードでは `Invalid`）。 |

### 5.2 内部ノード

内部ノードは最大 `MaxInternalKeys`（681）個の key と、key より 1 つ多い子ポインタを持つ。2 つの配列は**固定予約領域**を占める: 子配列は可変長の keys の直後ではなく**定数**オフセット（`ChildAreaOff = 5456`）から始まる。`key_count = N` が各々の生きている個数を記録し、領域の N を超えた末尾は予約された余白。

```
0        8                         5456 (ChildAreaOff)             8184
+--------+--------------------------+-------------------------------+--+
| header | keys[0..N-1]  (+ 余白)   | children[0..N]  (+ 余白)       |  |
|  8 B   | 領域 681 × 8 B           | 領域 682 × 4 B                |  |
+--------+--------------------------+-------------------------------+--+
         key i @ 8 + i·8            child i @ 5456 + i·4
```

子のベースが定数なので、key の挿入は keys の末尾を動かすだけで、子配列を移動させることはない（5.4 参照）。ノードは `key_count == MaxInternalKeys` のとき**満杯**。

separator の意味 — 子 `c[i]` はちょうど 1 つの key 帯を担当する:

```
       keys:      k0        k1        k2
   children:  c0     c1        c2        c3
      範囲:   <k0   [k0,k1)  [k1,k2)    ≥k2
```

`c[0]` は `< k0` の key、中間の `c[i]` は `[k[i-1], k[i])` の key、`c[N]` は `≥ k[N-1]` の key を持つ。これが子が key より 1 つ多い理由である。

### 5.3 葉ノード

葉は最大 `MaxLeafKeys`（584）個の key と、同数の TID（1:1 対応）を、内部ノードと同じく固定予約領域に持つ（TID 配列は定数 `TIDAreaOff = 4680`）。加えてヘッダーの `next_leaf` ポインタが葉を左から右へ連結して範囲走査を可能にする:

```
0        8                         4680 (TIDAreaOff)              8184
+--------+--------------------------+-------------------------------+--+
| header | keys[0..N-1]  (+ 余白)   | tids[0..N-1]  (+ 余白)         |  |    header.next_leaf ─► 次の葉
|  8 B   | 領域 584 × 8 B           | 領域 584 × 6 B                |  |
+--------+--------------------------+-------------------------------+--+
         key i @ 8 + i·8            tid i @ 4680 + i·6
```

`key_count == MaxLeafKeys` のとき満杯。各 `tids[i]` は、インデックス対象列が `keys[i]` に等しい行のヒープアドレス。検索の解決とは「葉で key を見つけ、並んだ TID を読み、`heap.Get(tid)` する」こと。

### 5.4 なぜスロットディレクトリが無いか

スロット付きページがスロット**ディレクトリ**を必要とするのは tuple が可変長だからで、ディレクトリは各 tuple のバイトを指す間接であり、tuple がページ内で移動しても参照を壊さない。v1 の B+Tree ノードは**定長**エントリ — `int64` key、`PageID` の子、`heap.TID` の値 — なので、ノードはヘッダー + 2 本のソート済み配列に還元される。要素 `i` の位置は純粋な算術（`base + i · size`）、二分探索は key 配列だけに触れる。ディレクトリも間接も無い。

2 本の配列は交錯（`key, ptr, key, ptr, …`）ではなく**分離**（全 key、続いて全ポインタ）で格納する。二分探索は key だけを走査するので詰めておく方がキャッシュに良く、また「N 個の key、N+1 個の子」という非対称を配列レイアウトが素直に吸収する — ポインタ配列が単に 1 要素長いだけ。

### 5.5 固定予約領域（なぜ第 2 配列のオフセットが定数か）

ポインタ／TID 配列は keys の直後ではなく**定数**オフセットから始まる。もし keys の直後（`8 + 8·key_count`）から始めると、そのベースは key 挿入のたびに 8 バイト動く — つまり key を 1 つ挿すだけで**第 2 配列全体**が移動し、余計に `i·(ポインタサイズ)` バイトの移動が加わる（末尾、すなわちよくある追記／順次挿入のケースで最悪）。ベースを定数にすると 2 配列は**疎結合**になり、key 挿入は keys の末尾だけ、値挿入は値の末尾だけを動かす。

これは追加の空間を消費しない。どちらのレイアウトも満杯でないノードに残る空きバイト総量は同じで、固定レイアウトはその空きを（ページ末尾の 1 つの隙間ではなく）2 つの末尾（keys の後・値の後）に分けるだけ。しかも key と値はここでは常に一緒に増える（`N` と `N`/`N+1`）ので、詰めたレイアウトが提供しうる「共有の弾力予算」は決して役に立たない。ソート配列ノードは挿入ごとに `O(N)` の末尾シフトを払う（ソートを保つ以上不可避）が、固定領域が消すのは第 2 配列全体の余分な移動だけ — 定数倍の改善。

（可変長 / `Text` の key はノード内にディレクトリ的な間接を再導入する。延期 — 負債参照。）

### 5.6 扇出と高さ

固定容量は 8192 バイトの予算から来る:

- **内部:** `8 + 8N + 4(N+1) ≤ 8192` → `N ≤ 681`（`MaxInternalKeys`）、すなわち最大 **682 子**。
- **葉:** `8 + 8N + 6N ≤ 8192` → `N ≤ 584`（`MaxLeafKeys`）、すなわち最大 **584 エントリ**。

この扇出だと木は極めて浅い:

| 層数 | 容量（オーダー） |
| :--- | :--------------- |
| 1（葉のみ） | ~584 key         |
| 2 | ~682 × 584 ≈ **40 万**    |
| 3 | ~682² × 584 ≈ **2.7 億**  |
| 4 | ~682³ × 584 ≈ **1800 億** |

したがって点検索はどんな現実的テーブルでも 3〜4 ページ読み。

## 6. 操作（v1）

| 操作 | 挙動 |
| :-- | :-- |
| `Insert(key, tid) → error` | key → TID エントリを挿入、必要に応じノード分裂。重複時は `ErrDuplicateKey`（唯一 key、v1）。 |
| `Search(key) → (TID, bool, error)` | 点検索。`bool` は key の存在有無。 |
| `Scan(lo, hi, fn) → error` | `lo ≤ key ≤ hi` の全エントリを key 順に訪れ、`fn(key, tid)` を呼ぶ。 |

### 6.1 検索（点）

root（`meta.root_pid` から）で開始。各内部ノードで key を二分探索し `i = upper_bound(keys, K)`（`K` 以下の key 数）を求め、`children[i]` を読み、子を `FetchPage`。葉では `K` を二分探索: 見つかれば TID を返し、無ければ not found。各層は二分探索 1 回 + 子ポインタへの平行移動 1 回。

### 6.2 範囲走査

点検索と同様に、`lo` を含むはずの葉まで下降。`≥ lo` の最初のエントリから葉の配列を歩き `fn` を呼び、葉の末尾で `next_leaf` を辿って次の葉へ。key が `hi` を超えたら停止。葉の連結が、範囲走査で上位層に戻らずに済む理由。`heap.Scan` と同様、`fn` はエラーを返して早期停止でき、I/O エラーも外へ伝播する。

### 6.3 挿入と分裂

（検索と同様に）対象の葉まで下降し、`(key, TID)` をソート位置に挿入、配列の末尾を 1 つずらす。まだ収まれば完了。溢れたら**分裂**し、分裂は上へ連鎖しうる。ドライバは再帰的で、挿入は親が吸収する任意の分裂結果 `{sepKey, rightPID}` を返す。

**葉の分裂 — copy-up。** 満杯の葉を 2 つに分け、新しい右葉の先頭 key を separator として親へ**コピー**する。key 自体は葉に残る — 葉は本物のデータを持ち、何も失ってはならないから。`next_leaf` の連結を修復する: `right.next = left.next; left.next = right`。

**内部の分裂 — push-up。** 満杯の内部ノードを 2 つに分け、**中央**の key を親へ**移動**する — どちらの半分にも残さない。内部 key は separator に過ぎず、昇格した中央 key が 2 つの半分の間の正確な separator になるから。子ポインタは key と一緒に分かれる。

**root の分裂 — 頂上で伸びる。** 分裂が root に届き root 自身が分裂したら、**新しい root**（separator 1 つ、子 2 つ）を作り `meta.root_pid` を更新する。これが木が高くなる**唯一**の方法: 頂上から伸び、全葉を一緒に 1 層押し下げる。

**平衡不変条件。** 生長は root でのみ起き全葉が足並みを揃えて下がるため、**全葉は常に同じ深さ**にあり、挿入順に依存しない。不平衡な BST のように B+Tree が高く不平衡な木に退化することはない。挿入のみのワークロードでは分裂で各半分が少なくとも約半分埋まるため、ノードが空に近づくことはない。半分ルールを免除される唯一のノードは root（新しい root は構造上 key 1 つ）。

## 7. 依存関係

**`pager` インタフェース。** ヒープと同様、B+Tree は具体型 `*buffer.BufferPool` ではなく小さな消費者側インタフェースに依存する:

```go
type pager interface {
    FetchPage(pid disk.PageID) (*page.Page, error)
    NewPage() (*page.Page, disk.PageID, error)
    UnpinPage(pid disk.PageID, dirty bool) error
    NumPages() disk.PageID
}
```

プールは生フレームを供給し、`nbtree` がノードビューを被せる。下降は 1 層につき 1 ページを pin し、子の分裂を吸収するまで親を pin したまま保持するので、**インデックスプールのフレーム数は木の高さより多くなければならない**。

**`heap.TID`。** 葉の値はヒープの行アドレスなので `heap.TID` として型付けする（v1 は直接 import。依存 `nbtree → heap` は非循環）。TID を中立な共有パッケージへ切り出すのは延期（負債参照）。

## 8. 延期（将来の置き場所つき）

- **削除** — 平衡のアンダーフロー側が必要: ノードが半分未満になったら兄弟と**マージ**または**再分配**する。ヒープの削除同様 MVCC も待つ。無くても削除は空間を浪費するだけで、木を高くすることはない。
- **重複 key** — v1 は唯一 key を要求。非唯一インデックス（1 つの key 値に多数の行）は分裂／検索での重複 key 処理が要る。
- **可変長 / `Text` key** — ノード内にディレクトリ的な間接を再導入する。v1 の key は定長 `int64`。
- **複数ファイル共有プール** — v1 はインデックスに専用ファイル上の専用プールを与える。ヒープ + インデックスを 1 プールで担うには複合キー `{fileID, pid}` が要る（バッファプールの負債）。
- **`TID` の中立な置き場所** — 現状 `heap.TID`。共有の物理行アドレス型があれば 2 つのアクセスメソッドを疎結合にできる。
- **双方向連結の葉 / バルクロード** — v1 は葉を前方向のみ連結。順次バルク挿入はノードを約半分埋めで残す（空間の問題であって高さの問題ではない）。
